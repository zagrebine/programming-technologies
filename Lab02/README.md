# Лабораторная работа №2 - Основы ООП

## Описание

В рамках лабораторной работы реализована базовая иерархия классов для пошаговой стратегической игры.

Основная цель работы - применить основные принципы объектно-ориентированного программирования: наследование, инкапсуляцию, полиморфизм и использование интерфейсов для описания различных возможностей игровых объектов.

Проект реализован на **Java**.

---

## Архитектура

В качестве базового класса используется `GameObject`. От него наследуются все остальные игровые объекты.

Основная иерархия выглядит следующим образом:

* `GameObject`

    * `Unit`

        * `Archer`
    * `Building`

        * `Fort`
        * `MobileHouse`

Для описания отдельных возможностей объектов используются интерфейсы:

* `Attacker` - объект может атаковать другую сущность;
* `Damageable` - объект может получать урон;
* `Moveable` - объект может изменять своё положение.

Таким образом, различные возможности не привязаны непосредственно к иерархии наследования.

Например:

* `Archer` является `Unit`, умеет атаковать и перемещаться;
* `Fort` является `Building` и умеет атаковать;
* `MobileHouse` является `Building` и умеет перемещаться;
* `Unit` реализует `Damageable`, поэтому может получать урон.

## Основные классы

### GameObject

Базовый класс для всех игровых объектов.

Хранит общую информацию:

* идентификатор;
* имя;
* координаты `X` и `Y`.

Предоставляет методы для получения этих данных.

### Unit

Наследуется от `GameObject` и представляет управляемый игровой юнит.

Содержит:

* количество здоровья (`HP`);
* состояние жизни юнита, определяемое по текущему значению здоровья.

Реализует интерфейс `Damageable`.

При получении урона здоровье уменьшается, при достижении нуля юнит считается погибшим. Отрицательное значение здоровья не допускается.

### Archer

Наследуется от `Unit`.

Реализует:

* `Attacker`;
* `Moveable`.

Лучник может атаковать объект, способный получать урон, и изменять свои координаты.

### Building

Наследуется от `GameObject`.

Представляет базовый класс для построек и содержит состояние, определяющее, построена ли конкретная постройка.

### Fort

Наследуется от `Building` и реализует `Attacker`.

Крепость может атаковать противника и наносить ему урон.

### MobileHouse

Наследуется от `Building` и реализует `Moveable`.

Представляет дом на колёсах, который, в отличие от обычной постройки, может перемещаться по игровому полю.

## Интерфейсы

### Attacker

Описывает способность объекта атаковать.

В исходном ТЗ метод `attack` принимал конкретно `Unit`. В реализации параметр был расширен до `Damageable`.

Такое изменение позволяет атаковать не только объекты конкретного класса `Unit`, а любые объекты, реализующие способность получать урон.

Это уменьшает связанность между классами: атакующему объекту не требуется знать конкретный тип цели, ему достаточно знать, что цель поддерживает `Damageable`.

### Damageable

Интерфейс был добавлен в процессе реализации для выделения отдельной способности объекта - возможности получать урон.

`Unit` реализует данный интерфейс.

Это также позволяет использовать полиморфизм при атаке: `Attacker` работает с контрактом `Damageable`, а не с конкретной реализацией объекта.

### Moveable

Описывает способность объекта перемещаться по игровому полю.

Его реализуют `Archer` и `MobileHouse`.

## Отличия от исходного ТЗ

В процессе реализации были внесены небольшие архитектурные изменения относительно первоначального задания.

Главное изменение - введение интерфейса `Damageable`.

В исходном ТЗ `Attacker` должен был принимать объект типа `Unit`. В реализации вместо этого используется `Damageable`.

Причина такого изменения - разделение ответственности:

* `Attacker` отвечает за возможность атаковать;
* `Damageable` отвечает за возможность получать урон.

Таким образом, классы зависят от необходимых им возможностей, а не от конкретных классов.

Также состояние жизни `Unit` не хранится в отдельном поле. Метод `isAlive()` определяется на основании текущего значения `HP`: если здоровье больше нуля, юнит считается живым. Это позволяет избежать рассинхронизации между `HP` и состоянием объекта.

При получении урона значение `HP` ограничивается снизу нулём.

## Принципы ООП

В реализации используются основные принципы ООП:

**Наследование** - общая функциональность вынесена в `GameObject`, `Unit` и `Building`, после чего конкретные классы расширяют соответствующее поведение.

**Инкапсуляция** - состояние объектов хранится внутри классов, а доступ к нему осуществляется через публичные методы.

**Полиморфизм** - объекты работают через интерфейсы `Attacker`, `Damageable` и `Moveable`, поэтому конкретная реализация может отличаться.

**Абстрагирование** - интерфейсы описывают способности объектов без привязки к конкретному классу.

## Проверка работы

Для проверки реализации создан класс `Main`, который демонстрирует основные возможности системы:

* создание игровых объектов;
* получение идентификаторов, имён и координат;
* получение и изменение здоровья юнитов;
* атаку лучника;
* атаку крепости;
* перемещение лучника;
* перемещение мобильного дома;
* проверку состояния построек;
* проверку смерти юнита при достижении нулевого здоровья.

Все основные сценарии выполняются корректно, программа завершается без ошибок.
